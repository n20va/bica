# Структура проекта, агента и защиты

Ниже — предлагаемая структура будущей реализации. Сейчас созданы только документы планирования; экспериментального кода и результатов в этих папках ещё нет.

## Структура репозитория

```text
bica/
  README.md                    # задача, установка, команды, результаты
  pyproject.toml               # зависимости и версия Python
  configs/
    pilot.yaml                # модели, условия, повторы, лимиты
    benchmark.yaml            # фиксированные настройки внешних тестов
  data/
    images/                   # исходные изображения
    manifest.csv              # ID, источник, группа, split, хеш
    annotations/              # эталоны; доступны только оценщику
    external/                 # версии и списки ID внешних наборов
  prompts/
    describe.txt
    alternative.txt
    verify.txt
    controller.txt
  src/illusion_agent/
    clients.py                # единый интерфейс разных VLM
    state.py                  # гипотезы, признаки, история решений
    agent.py                  # цикл работы вашего агента
    baselines/                # отдельные адаптеры опубликованных методов
    transforms.py             # преобразования и журнал параметров
    run.py                    # запуск одинаковых примеров всеми методами
    evaluate.py               # оценка сохранённых ответов
    report.py                 # таблицы и графики
  runs/<run_id>/
    config.json
    requests.jsonl
    responses.jsonl
    trace.jsonl
    metrics.csv
  reports/
    pilot.md
    final.md
    figures/
  tests/                      # метрики, разделение эталонов, лимиты
  docs/                       # план, протокол, архитектура
```

Для первого прототипа достаточно `clients.py`, `agent.py`, `run.py`, `evaluate.py`, нескольких промптов и CSV. Оформление полноценного пакета не должно задерживать первые проверяемые результаты.

## Как работает собственный агент

```text
Изображение + вопрос
        ↓
Первичное описание
        ↓
Память гипотез и визуальных признаков
        ↓
Контроллер выбирает следующий шаг
        ↓
Поиск альтернативы / просмотр другого масштаба / проверка признаков
        ↓
Обновление состояния → продолжить в пределах бюджета или завершить
        ↓
Ответ: подтверждённые интерпретации + признаки + неопределённость
```

Это один агент с несколькими перспективами рассмотрения: локальные детали, глобальная композиция, критическая проверка. Для такой архитектуры не обязательно использовать разные модели или чат нескольких персонажей.

Минимальная запись гипотезы: `id`, текст интерпретации, область изображения, наблюдаемый признак, источник наблюдения/версия изображения, контраргументы и статус. Контроллер не имеет доступа к эталонным ответам и не принимает решение по «правильности», известной только оценщику.

Пример правила для прототипа: после первого описания сделать один поиск альтернативы; проверить найденные гипотезы; в варианте 2 при отсутствии конкретной визуальной опоры запросить один дополнительный вид изображения и проверить заново; завершить по лимиту. Не требовать обязательно выдать два образа. Программная проверка JSON подтверждает формат, но не истинность визуального утверждения.

Для честного контроля дополнительных вычислений сравнить агента с обычной повторной проверкой при том же максимальном числе вызовов. Показывать фактический расход: равное число вызовов не гарантирует равного числа токенов или стоимости.

**Условный пример, не результат эксперимента:** на вазе Рубина первое описание — центральный сосуд; поиск альтернативы предлагает два профиля; проверка указывает, как границы сосуда образуют контуры носов и губ. Агент сохраняет обе интерпретации. На обычной фотографии чашки отсутствие подтверждённого второго образа должно быть допустимым итогом.

В основном сравнении агенту не подсказывать эталонную интерпретацию. Эксперимент с направленными подсказками — отдельное диагностическое условие: его результаты не означают самостоятельного обнаружения.

## Структура отчёта

1. Проблема: что такое визуальная неоднозначность и какую функцию улучшаем.
2. Обзор: опубликованные агенты, бенчмарки, чем предполагаемый вклад отличается.
3. Исследовательские вопросы и гипотезы, сформулированные до итогового теста.
4. Данные: источники, разметка, разделение, известные иллюзии и отрицательные примеры.
5. Метод: состояние агента, контроллер, схема, промпты, один полный пример.
6. Эксперимент: методы сравнения, модели, настройки, бюджеты и метрики.
7. Результаты: внешние бенчмарки отдельно; собственный набор отдельно; абстракция как пилот.
8. Анализ: полезность компонентов, влияние подсказок, ошибки и затраты.
9. Ограничения: малый набор, знакомые модели иллюзии, субъективность разметки, отсутствие доступа к внутреннему восприятию.
10. Выводы: что подтверждено, что не подтвердилось и в каких условиях метод полезен.
11. Приложения: точные промпты, версии данных, конфигурации, правила оценки и команды воспроизведения.

Фразу из исходного VLM-документа «работа не дублирует существующие исследования» лучше заменить на «предполагаемое отличие, которое проверяется обзором и сравнением». Художественный материал сам по себе ещё не гарантирует научную новизну.

## Презентация на 8 слайдов

1. Одна неоднозначная картинка и исследовательский вопрос.
2. Почему выбран этот тип неоднозначности; чему научил пилот с абстракцией.
3. Два внешних набора и собственная разметка.
4. Сравниваемые методы и ожидаемый вклад.
5. Схема агента и один пример его действий.
6. Главная таблица качества, ложных альтернатив и затрат.
7. Отключение компонентов и 2–3 характерные ошибки.
8. Выводы и ограничения.

## Разделение работы на пятерых

| Роль | Проверяемый результат |
| --- | --- |
| Данные | Manifest, источники, разделение, организация независимой разметки |
| Обзор и baseline-агенты | Два воспроизводимых опубликованных агентных метода и SemVink |
| Собственный агент | Состояние, контроллер, промпты, трасса одного примера |
| Эксперимент и оценка | Единый запуск, метрики, контроль утечек, стоимость |
| Анализ и оформление | Таблицы, графики, отчёт, демонстрация и презентация |

Разметку и оценку выполняют как минимум два участника независимо, несмотря на распределение технических ролей.

## Критерий готовности

Проект готов к защите, когда другой человек может по инструкции запустить сравнение, увидеть одинаковый состав тестов, пересчитать метрики по сохранённым ответам и проследить хотя бы один полный пример решения. Нужны собственный агент, два опубликованных агентных сравнения, два внешних бенчмарка и честный анализ, включая отсутствие улучшения, если именно оно получено.
